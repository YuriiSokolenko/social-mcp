# GitHub Actions diagnostics

Pi's model and runtime event stream is rendered by `scripts/pi-log-filter.mjs`. Focused check output is built in `scripts/pi-common/run-check.mjs`; stage failures are persisted by `scripts/pi-agent-runtime.mjs` and uploaded by every workflow that runs a Pi stage.

## Investigation of information loss

| Source | Cause | Handling |
| --- | --- | --- |
| Model and tool detail | The log filter caps streamed turn text (24,000 chars), Job Summary turn fields (20,000 chars), tool arguments/results (4,000/8,000 chars), and final text (12,000 chars). These are deliberate UI bounds; before this change, the full failed or shortened tool event had no complete sanitized diagnostic copy. | Failed calls and shortened details are appended as sanitized JSONL records. Oversized tool detail states its displayed and complete lengths and points to the event record. Successful short calls do not duplicate their payload in the artifact. Model trace artifacts remain the source for provider exchanges. |
| Nested runtime output | GitHub `::group::` output is folded and only reliably navigable one level deep. The log filter used groups for response and tool detail, which could hide the primary error. | Tool failures now print their heading and bounded details outside a group. Successful detail remains grouped. Prefixes carry stage/call context. |
| `run_check` output | The result intentionally returned only 3,000-character stdout/stderr tails, and the subprocess collector discarded bytes beyond 4 MiB. This was the largest source of irrecoverable check diagnostics. | Each stream is spooled to a temporary file up to 32 MiB while the process continues draining output and keeping bounded in-memory tails. Failing, timed-out, and truncated checks append the captured sanitized output to the diagnostics artifact and return its event reference. Output beyond the spool cap includes omitted-byte counts and an explicit truncation marker; spool setup/write failures fall back to the bounded tail and mark capture incomplete without changing the check result. |
| Secret handling | Key-based masking, bearer/private-key/token masking in the log filter is intentional and must remain in place. | Diagnostic artifact serialization applies equivalent redaction, including exact values of secret-named environment variables, before writing. Artifact-write failures are best-effort and do not change check outcomes. |
| Multiline data | Pretty-printed JSON and subprocess output naturally span lines; lines are prefixed in the console and machine markers remain single-line JSON. | Keep the concise event header visible, then show bounded labeled details. The artifact stores full structured JSONL records. |
| ANSI and carriage returns | Pi stream rendering handles `\r`, `\n`, and `\r\n`; color codes are emitted only for tty/GitHub rendering. The check collector receives subprocess bytes and does not interpret terminal control sequences. | No semantic change to captured process output. |
| Shell and provider formatting | Shell pipelines can omit or transform data before it reaches Pi; provider errors and raw request/response bodies are owned by the existing model trace proxy. | Run-check spooling begins at the child stdout/stderr boundary. Provider request/response preservation remains in the raw model trace artifact; secrets there retain existing redaction. |

## Artifact lookup

Open `pi-diagnostics-<stage>-<run-id>-<attempt>.jsonl` from the workflow's sanitized runtime diagnostics artifact (7-day retention). Issue-agent, PR-fix, triage, dispatcher, architect, and PR-review workflows all upload this artifact; the artifact name also carries the issue or PR number for the `implementer`, `repair`, and `reviewer` stages (`pi-diagnostics-<stage>-<number>-<run-id>-<attempt>`). Console references use `filename#event-id`; IDs include process, phase, call, and a local sequence. Each JSONL record has an event type, stage/call, timestamp, and sanitized details. Existing machine-readable marker contracts are unchanged. The original model trace artifact remains uploaded separately.

The console summaries use `[PI][phase/call]` prefixes. Planner, implementer, coding, check, recovery, and final-failure summaries use their own `[PI][component]` prefixes. Failed tool summaries are outside a collapsed group; failed checks include status, exit code, failure count, and duration. Final failure lines include lifecycle, failure category, last tool/check, worktree preservation state, usage totals, and a diagnostics reference.

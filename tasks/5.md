# Threads: replies, mentions and search

## Scope and acceptance
## Goal
Implement permitted read tools for replies, mentions and keyword search on top of the authenticated Threads MCP read layer, and gracefully report unavailable capabilities when the connected app lacks a required permission.

## Acceptance criteria
- Implement `threads_list_replies`, `threads_search` and `threads_list_mentions` Threads MCP tools following docs/threads-tool-contract.md, building on the profile/posts read foundation of issue #3.
- Capability-gate each tool: when the connected app/account lacks the required permission, return a clear `capability_unavailable` (or `permission_required`) error rather than silently degrading; the capability tool must report whether replies, search and mentions are available.
- Preserve explicit pagination (limit/cursor) and stable normalized result/pagination fields.
- Keep platform API details inside the independent Threads adapter; keep the MCP/HTTP layers thin.
- Use mocked API boundaries in all automated tests; tests must not perform live Threads calls or publish/receive content.

## Tests
Cover authorized and denied responses with mocked HTTP calls, including pagination and unsupported/missing permission cases. Run pytest and Ruff.

## Out of scope
No publishing, reply-management, repost/quote or delete mutations (covered by issues #6/#7). No new OAuth flow or credential handling. No live platform API calls in CI.

## Acceptance notes
None of `threads_list_replies`, `threads_search` or `threads_list_mentions` is implemented yet in the current repository; this is unimplemented work that follows the profile/posts read tools (#3) per the Phase 1 order in `docs/threads-tool-contract.md`. The Threads adapter, MCP tools and OAuth do not yet exist (built in #16/#15/#17/#18/#3). No external API grants or production writes are invented.
